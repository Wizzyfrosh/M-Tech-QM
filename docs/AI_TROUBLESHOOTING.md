# AI generation reliability

Gemini defaults to `gemini-3.5-flash-lite`; `GEMINI_MODEL` can override it on the server. Google now restricts Gemini 2.5 models to previous active users and recommends 3.5 Flash-Lite or 3.8 Flash for new projects ([model documentation](https://ai.google.dev/gemini-api/docs/models)). The app previously hardcoded 2.5 Flash-Lite, making recent accounts susceptible to model-access rejection. Gemini requests omit deprecated sampling parameters ([migration guide](https://ai.google.dev/gemini-api/docs/whats-new-gemini-3.6)).

The instructor opens a draft quiz, pastes lesson notes and requests questions. The authenticated, same-origin API reserves one daily request and calls the chosen server-side provider. Output must pass exact-count, unique-options and source-excerpt checks before it reaches the editor. Adding suggestions leaves them unreviewed; saving and publishing remain explicit instructor actions.

Automatic mode tries configured Gemini, OpenRouter and xAI providers in order, including when the provider field is omitted by an internal caller. Each provider gets one attempt bounded to 40 seconds, including response consumption. Three providers can take about two minutes; the route allows 180 seconds for authentication, database work and provider calls. Individual selection calls only that provider. Invalid or unsupported lesson output stops generation rather than bypassing validation through another provider.

The previous OpenRouter timeout escaped as a native exception, which stopped automatic fallback. Production generation records showed failures at approximately 25 seconds. The route's previous 60-second duration also could not cover its possible provider retry/fallback sequence. Network and timeout failures now become recoverable availability errors, Gemini no longer consumes the fallback budget with a duplicate attempt, and all-provider failures identify each provider's safe error category.

Provider errors distinguish key/access rejection, credits, rate limits/quota, unavailable model, rejected settings and network/timeout problems. Provider response bodies, keys and lesson text are never logged. `QMS_AI_PROVIDER_FAILED` logs only the provider identifier and a fixed category. HTTP 400 can indicate key or request settings; check the provider dashboard for its precise explanation. No code change can replenish an external provider's credits or grant model access.

The existing quota remains ten generation requests per instructor per UTC day, including failed requests. An automatic fallback sequence uses one reservation. Transcripts remain in browser memory after failure and are not persisted by this endpoint. Authentication and published-quiz restrictions are unchanged.

Tests cover timeout and response-body failures, automatic recovery through the third provider, omitted-provider defaults, explicit provider isolation, grounded-output rejection, error redaction, quota accounting and persistence of generation status. The browser test uses a synthetic transport fixture to verify failure/retry, preserved notes and editable unreviewed questions; it does not establish real provider availability, credits or inbox behavior.
